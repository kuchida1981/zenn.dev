`yay -Syu` でシステム更新をしていたら、見慣れないパッケージのビルドがいつもよりかなり長くかかっていることに気づいた。調べてみると、**元は公式リポジトリから配布されていたパッケージが、ある日を境にAUR版へ静かに切り替わっていた**、という話だった。

Arch Linuxでは起こり得る現象だが、気づきにくく、切り替わった瞬間を後から特定するのも簡単ではなかったので、調査の過程と再利用できるチェック方法をまとめる。

# 環境

- Arch Linux (rolling release)
- KDE Plasma (Waylandセッション専用で運用)
- yay 13.1.0

# 現象

`yay -Syu` の中で、`kgamma` / `kwin-x11` / `wacomtablet` という3パッケージが更新対象になっていたが、どれも自分で `yay -S` した記憶が無かった。シェル（fish）のコマンド履歴にも、これらを個別にインストールしたコマンドは見つからない。

とはいえ `pacman -Qi` では `Install Reason: Explicitly installed`（明示的にインストールされたパッケージ）と表示されており、何かのパッケージの依存として入ったわけでもなさそうだった。

# 調査

## 1. 本当に依存パッケージではないかを確認する

まず、明示的にインストールされたAURパッケージと、依存として入ったAURパッケージを分けて確認した。

```bash
# 明示的にインストールされたAUR(foreign)パッケージ一覧
pacman -Qqem

# 依存として入ったAUR(foreign)パッケージ一覧
pacman -Qqdm
```

`pacman -Qi <パッケージ名>` の `Required By` が3つとも `None` だったため、他のどのパッケージからも依存されていない、純粋に独立したパッケージだと確認できた。

## 2. いつ・何として入ったのかを遡る

記憶にないなら過去のどこかで何かと一緒に入ったはずだと考え、`/var/log/pacman.log` を遡った。

```bash
grep -E "(installed|upgraded) kgamma |installed kwin-x11 |installed wacomtablet " /var/log/pacman.log
```

3つとも同じ日時・同じトランザクションの中で、`kdeplasma-addons` や `spectacle`、`xf86-input-wacom` など多数のKDE関連パッケージと一括インストールされていたことがわかった。おそらくPlasmaデスクトップ環境を一括セットアップした際にまとめて入ったもので、個別のコマンドとして記憶に残らなかったのも納得できる。

## 3. 「公式→AUR」への切り替わりを確認する

ここが本題。`pacman -Si` で公式リポジトリの情報を見てみる。

```bash
$ pacman -Si kgamma
エラー: パッケージ 'kgamma' は見つかりませんでした
```

3パッケージとも同様に「見つかりません」。つまり**公式リポジトリからは完全に削除されている**。一方 `yay -Si` でAUR側を見ると、投稿日が調査時点からわずか2日前になっていた。

```bash
$ yay -Si kgamma
...
最初の投稿 : 2026年11月17日
メンテナ    : (有志のAURメンテナ)
```

ウェブで経緯を確認したところ、KDE Plasmaが新しいバージョンでX11セッションのサポートをアップストリームで完全に終了し、Wayland専用になったことが背景にあるようだった。`kwin-x11`（X11用ウィンドウマネージャ本体）、`kgamma`（X11専用のガンマ補正ツール）、`wacomtablet`（旧来のWacomタブレット設定モジュール）は、いずれもこのX11レガシー機能に当たる。公式リポジトリでの提供終了に合わせて、有志がAURで同名パッケージを再公開し、更新を継続できるようにしていた。

:::message
「KDE側がこの3つを名指しでアナウンスした」という部分はフォーラムの二次情報であり、一次ソース（公式アナウンス）までは確認できていない。
:::

## 4. 「いつ切り替わったか」をローカルの証拠から特定する

もう一つ気になったのは、この切り替わりが実際にいつ起きたのかだった。`pacman.log` はパッケージ名とバージョンの変化しか記録せず、どのリポジトリ由来かまでは記録しないため、ここからは判断できない。

代わりに役立ったのが `yay` 自身のビルドキャッシュだった。

```bash
$ ls -la --time-style=full-iso ~/.cache/yay/kwin-x11
```

`yay` はAURパッケージをビルドする際、必ず `~/.cache/yay/<パッケージ名>/` にAURリポジトリをgit cloneする。3パッケージのディレクトリのタイムスタンプを見ると、同一の日時（2026-11-18 20:00）が記録されていた。これはその瞬間に初めてAUR版としてビルドされたことを示しており、今回の「ビルドが長かった」の正体がここにあったとわかった。

ちなみにシェル（fish）の履歴で `yay -Syu` を実行した時刻を調べたところ、キャッシュのタイムスタンプとは数時間ずれていた。これは**fishの履歴が同一コマンドの再実行時に古いタイムスタンプを上書きする**仕様によるものと考えられる。`yay -Syu` のように何度も同じコマンドを打つ操作では、履歴の実行時刻を鵜呑みにせず、キャッシュディレクトリのような物的証拠を優先した方がよい。

# 対処

このマシンはWaylandセッション専用で運用しており、

- `kwin-x11`（X11用ウィンドウマネージャ）→ そもそもX11セッション自体がログイン画面の選択肢に存在しなかった
- `kgamma`（X11専用のガンマ補正）→ Waylandでは機能しない
- `wacomtablet`（Wacomタブレット設定）→ タブレット自体を使っていない

という状況だったため、`pacman -Rs --print` で依存の連鎖を確認した上で削除した。

```bash
sudo pacman -Rns kgamma kwin-x11 wacomtablet
```

# 汎用化できるチェック方法

同じような「身に覚えのないAURパッケージのビルド」に遭遇したときのために、判断の手順を整理しておく。

1. **依存関係の確認**: `pacman -Qi <pkg>` の `Required By` が `None` なら、何かの依存ではなく独立してインストールされている
2. **公式リポジトリに今も存在するか**: `pacman -Si <pkg>` がエラーになれば、公式リポジトリから削除されている
3. **いつAUR版としてビルドされたか**: `ls -la --time-style=full-iso ~/.cache/yay/<pkg>` のタイムスタンプが、実際の切り替わりの瞬間を示す
4. **今本当に必要か**: `Required By` / `Optional For` に加え、該当機能（今回ならX11セッションやWacomタブレット）を実際に使っているかを確認してから削除を判断する

# 所感

AURパッケージは「自分が明示的に選んだもの」だけとは限らず、**公式リポジトリがパッケージの提供をやめた結果として、気づかないうちにAUR版へ切り替わっている**ことがある。Arch Linuxのローリングリリースという性質上、パッケージの出自が静かに変わること自体は珍しくないのだろうと思うが、ビルド時間が急に伸びたときに「あれ、これ自分で入れたやつだっけ?」と疑う価値はある。

`fish_history` のようなシェル履歴は便利だが、同一コマンドの再実行で上書きされるなど過信できない部分もあるため、`pacman.log` や `~/.cache/yay/` のようなシステム側に残る記録と併用するのが確実だと感じた。
