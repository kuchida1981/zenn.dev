## TL;DR

* Notion を Gemini から使うために、OAuth 2.1 + Streamable HTTP の MCP サーバー(ファサード)を Cloud Run に自作した
* Gemini から使うと「Notion へ接続しています」のまま止まる、「エラーが発生しました (1)」が出る、といった不安定さがあった
* サーバー側のログ・遅延・トークン・スキーマ・SSE・セッションを順に検証したが、**サーバーは毎回正常に応答していた**
* それでも Gemini 側でツールが使われる確率は 2〜3 割程度。同じ入力でも成否が入れ替わる
* 現時点では **Gemini 側の MCP クライアント実装(または接続処理)に原因がある可能性が高い**と考えている(断定はできない)

## 何を作ったのか

Gemini から Notion を使いたいものの、Gemini が要求する認証方式(OAuth)にそのままでは対応できないため、間に薄いサーバーを挟みました。

* Hono + Node 22 / TypeScript
* OAuth 2.1(動的クライアント登録、PKCE、アクセストークンは JWT、リフレッシュトークン)
* MCP は Streamable HTTP をステートレスで提供(`@modelcontextprotocol/sdk`)
* ストアは Firestore、実行は Cloud Run(min instances 0)
* Notion API は 2025-09-03 版(data_sources)

## 症状

Gemini Web で `@Notion` を使って Notion のページを検索させると、次のような症状が出ました。

* 「常に許可」を設定しているのに、許可を求める表示が出る
* 「Notion へ接続しています」の表示のまま 20〜30 秒止まる
* 「エラーが発生しました (1)」と出る(ヘルプにも `(1)` の説明は見当たらない)
* サーバー側でツールが成功しているのに、Gemini は「Notion のツールが使えない」と回答する

## 調査方法

Chrome を操作して Gemini に同じ依頼を繰り返し送り、サーバー側の観察ログと突き合わせました。

* Firestore に `events` コレクション(30 日 TTL)を用意し、各リクエストについて次を記録
  * エンドポイント、ステータス、処理時間
  * MCP の `rpc_method` と `tool_name`、結果サイズ、ツールエラーの有無
  * ヘッダの要約(`Mcp-Protocol-Version`、User-Agent など)
* トークン、ツール引数、応答本文は**記録しない**
* あわせて Cloud Run のログも確認

## まずサーバーの穴を直した

調査の途中で、症状と関係しそうなサーバー側の弱点を見つけて直しました。

| 内容 | 目的 |
|---|---|
| Notion API にタイムアウト(10 秒)と 429/5xx のリトライを追加 | 外部 API の遅延で固まらないように |
| `/mcp` の 500 を JSON-RPC 形式で返す、401 に `error="invalid_token"` を付与 | クライアントが原因を判別できるように |
| events 書き込みの待ち時間に上限(1.5 秒) | ログ書き込みが応答を遅らせないように |
| ブロック子要素の取得を並列化(同時 3) | ページ本文取得の遅延対策 |
| レート制限の IP 判定を `X-Forwarded-For` の末尾に | Cloud Run では末尾が実クライアント IP のため |

これらは直して良かったものの、**Gemini の症状自体は変わりませんでした**。

## サーバーは健全だった(確定したこと)

ログから、次のことがはっきりしました。

* 応答は常に 200/202 で、処理時間は 20〜600 ms(Notion API 呼び出しを含む `tools/call` でも 300〜1400 ms)
* トークンの更新は正常で、再認可や 401 は発生していない
* ツールの失敗は一度も記録されていない。検索結果も正しく返している
* コールドスタートの有無に関係なく再現する(常時 1 インスタンスにしても効果は見込めない)

## Gemini 側の挙動(観察)

ログから見えた Gemini 側の動きは、次のとおりです。

* `Mcp-Protocol-Version: 2025-11-25` で、User-Agent は `Google`
* 同じリクエストを 2〜3 本、並列で重複して送る(`initialize`、`tools/call` とも)
* 毎回 `GET /mcp`(SSE 用の接続)を試し、405 を受ける
* 多くの回で、`initialize` を送らずに `tools/list` を単独で送る
  * その後 10〜19 秒空けて `initialize` → `tools/call` に進む回(成功)と、何も続かずに「使えない」と回答する回(失敗)がある
* 失敗の約 20 秒後に `GET /revoke`(404)が届くことがある

同じ入力・同じサーバー状態でも、成功と失敗が入れ替わるのがポイントです。

## 仮説を一つずつ潰す(実験)

「仕様の解釈や応答形式の違いで、Gemini が嫌がっているのかもしれない」と考え、実験用の環境変数スイッチを用意して本番で切り替えました。

| 実験 | 内容 | `tools/call` が届いた割合 |
|---|---|---|
| 基準 | 変更なし | 約 2〜3 / 9 |
| SSE 応答 | POST の応答を `text/event-stream` にする | 0 / 2 |
| スキーマ簡略化 | `tools/list` から `$schema` / `execution` / `additionalProperties` を除去 | 3 / 7 |
| セッション発行 | 署名付き `Mcp-Session-Id` を発行し、欠落は 400 で拒否 | 2 / 4 |

セッション実験では、`initialize` なしの `tools/list` を 400 で拒否すると、Gemini は約 0.2 秒で `initialize` に進み、以降のリクエストにセッション ID を付けました。つまり**標準どおりの動きは取れる**クライアントです。ただし、成功率は改善しませんでした。

サンプル数が小さいため、効果が小さい場合は検出できていない可能性があります。「効果がなかった」ではなく「大きな効果は見つからなかった」と読むのが正確です。

## 結論: Gemini Web の MCP クライアントが怪しいのか

* サーバー側では、遅延、トークン、ツールエラー、スキーマ、応答形式、セッションのどれも原因として特定できなかった
* ツール呼び出しの前後でサーバーは常に成功しており、**ツールを使うかどうか(または接続処理)を判断する段階で失敗している可能性が高い**
* 「エラーが発生しました (1)」に対応するコードは、サーバーのレスポンスには存在しない。Gemini 側の汎用エラーと思われる

ただし、次の点は**未確認**です。

* Gemini 側の内部ログは見えないため、原因が Gemini のバグなのか、こちらの未知の非互換なのかは区別できない
* 「許可を求められる」症状が、ツール確認ダイアログなのか OAuth 認可画面なのかは切り分けられていない(調査中は再認可が発生しなかった)

## 補足: Antigravity CLI では起きない

筆者の環境では、Antigravity CLI から Notion 公式のリモート MCP を使うと、この問題は起きず、ふつうに使えています。リフレッシュトークンも、おそらく問題なく使われています(こちらはログを見ていないので推測です)。

「同じ Google 系のクライアントでも、Antigravity CLI では問題がない」という点は、Gemini Web の MCP クライアントに固有の事情がありそうだという見方を補強します。ただし、つないでいる先が自作ファサードではなく Notion 公式の MCP なので、「ファサードの側に原因がない」ことの証明にはなりません。切り分けるには、Antigravity CLI から自作ファサードにつないで同じ挙動になるかを確認する必要があります(未実施)。

## 個人的な感想(ここは完全に推測です)

根拠はなく、あくまで個人の印象ですが、Google が Notion への公式対応を積極的に進めるとは、あまり期待していません。Gemini の MCP 対応はまだ発展途上に見えますし、優先度が高いのは Google 自身のサービス連携だろう、と想像しています。そのため、当面は自前でファサードを置くような回避策に頼ることになりそうです。

## 運用上の割り切り

* 失敗したら、同じ依頼を再送すると通る回がある、という前提で使う
* コストを理由に、常時 1 インスタンスの起動は見送った(効果も見込めない)
* 観察結果(`initialize` なしの `tools/list`、並列重複、成功率のばらつき)は Google 側にフィードバックする

## 自作 MCP サーバーで Gemini 連携を試す人へのメモ

* 不安定なときは、まずクライアントのリクエストをサーバー側で記録できるようにしておくと、切り分けが一気に進む(今回の最大の収穫)
* その際、トークンや引数、応答本文を残さない設計にしておく
* Cloud Run ではレスポンス返却後に CPU が絞られるため、ログ書き込みを fire-and-forget にすると落ちることがある。待つなら上限時間を付ける
* `X-Forwarded-For` は先頭を信用しない(Cloud Run は実クライアント IP を末尾に追加する)
