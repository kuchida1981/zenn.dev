ノートパソコンにインストールしている Arch Linux + KDE Plasma で、Alt+Tab で表示されるタスクスイッチャーにウィンドウプレビューが表示されなくなってしまった。

画面イメージとしては[このような感じ](https://www.reddit.com/r/kde/comments/1kf6q66/no_window_previews_in_task_switcher_on_arch_kde/)（スクリーンショットがうまく撮れなかったので、Reddit の投稿を引用）。

同じ問題が、タッチパッドで3本指で上方向へスワイプしたときに表示される Overview でも起きる。

アイコンやタイトルは正常に表示され、ウィンドウの中身のプレビューだけが単色の四角のままになる。`kwin_wayland` のログにもエラーは出ていなかった。

# 環境

- Arch Linux (rolling release)
- KDE Plasma 6.8.1 / KWin 6.8.1 / Wayland セッション
- Qt 6.12.0、Mesa 26.2.5
- GPU: AMD Radeon Graphics (Barcelo/Renoir APU, radeonsi)

# 原因

いろいろ切り分けを行ったが（後述）、結論としては `~/.config/kwinrc` に入っていた次の設定が原因だった。

```ini
[QtQuickRendererSettings]
SceneGraphBackend=software
```

これを削除し、ログアウト→ログインしたところ、Alt+Tab・Overview ともにサムネイルが復活した。

AI ちゃんいわくですが、

> `kwinrc` の `SceneGraphBackend=software` が、**Qt Quick (QML) の描画エンジンを強制的にソフトウェアレンダラーに切り替えていた**ことが根本原因。
>
> この設定は Qt の自己保護機能で、過去に何らかの GPU ドライバ関連のクラッシュが起きた際、以降の安全のため自動的に書き込まれたものと推測される。

とのことだった。後半の「自動的に書き込まれた」という部分は AI の推測であり、裏は取れていない。

## なぜサムネイルだけ描画されなかったのか

これも AI による説明だが、次のとおり。

- アイコンやテキストなど通常の QML 描画は、ソフトウェアレンダラーでも問題なく動作する
- 一方、タスクスイッチャーと Overview が共通して使う `KWin.WindowThumbnail` は、内部で GPU 上のテクスチャを QML に直接取り込む処理（`createTextureFromNativeObject`）に依存している
- ソフトウェアレンダラー下ではこの処理が null を返す仕様のため、UI 自体は正常に動くのにウィンドウの中身だけが描画されない

パッケージのバージョンとは無関係なユーザー単位の設定 1 行が原因だったため、どのパッケージをダウングレードしても直らず、新規ユーザーでは再現しなかった（そもそもこの設定が存在しないため）という状況とも整合する。

# 対処方法

`~/.config/kwinrc` から次の2行を削除し、ログアウト→ログインし直した。

```ini
[QtQuickRendererSettings]
SceneGraphBackend=software
```

# 切り分けのために行ったこと

当初はパッケージ更新に伴う問題だと思い込んでいたため、AI と相談しつつ、次のことを行いながら検証・切り分けを行った。いずれも解決しなかった。

1. kwin, plasma-workspace, libplasma, kdeplasma-addons を 6.8.1 から 6.8.0 へダウングレード
2. mesa を 26.2.5 から 26.2.4 へダウングレード
3. kwayland, kwindowsystem を更新前バージョンにダウングレード
4. qt6-base, qt6-declarative を 6.12.0 から 6.11.2 へダウングレード
    * SDDM のログイン画面が壊れてログイン不可になり、Qt のロールバックはあきらめた（`sudo pacman -Syu` で復旧）
5. ディスプレイスケールを 125% から 100% へ変更
6. `~/.cache/mesa_shader_cache`, `~/.cache/kwin/qmlcache` を削除し再生成
7. `kwinrc` を一時的に初期化
8. ウィンドウ数を最小限（Konsole 2 枚など）にして再現確認
    * セッションの重さや開いているウィンドウ数は無関係だった

最後に、**検証用ユーザーを作成して切り替えたところ、問題が再現しなかった**。原因がシステム全体（パッケージ）ではなく、特定ユーザーの設定ファイルにあるとわかったので、検証用ユーザーのホームディレクトリと実ユーザーの設定ファイルを diff で比較し、`~/.config/kwinrc` にだけ存在する上記の設定を発見して解決した。

# 所感

Claude に付き合ってもらったためか、普段ならためらいそうになるパッケージバージョンのロールバックから試してしまい、「すわ上流のバグでは？」と結論づけそうになった。

ふと、自分が普段こういうケースでどう切り分けていたかを考えて、ダミーのユーザーを作成して試したところ、解決に至った。ユーザープロファイル系の問題なのか、パッケージに起因する問題なのかは、こういう切り分け方が有効であることを思い出した。

- パッケージのダウングレードで切り分かない症状は、ユーザー固有の設定ファイル（`kwinrc` など）を疑う価値がある
- 新規ユーザーを作って同じ現象が起きるか確認するのは、「システム全体の問題」か「そのユーザーの設定の問題」かを一発で切り分けられる強力な手法
- サムネイルだけが壊れ、他の UI は正常でログにもエラーが出ない場合は、QML スクリプトの不具合ではなく「GPU テクスチャの受け渡し」のようなネイティブ連携部分を疑うとよい
- `qt6-base` / `qt6-declarative` のような中核パッケージだけを個別にダウングレードすると、他の Qt6 系パッケージとの不整合で SDDM ごと壊れるリスクがある。ロールバックで検証する際は、影響範囲の小さいものから順に試すこと
